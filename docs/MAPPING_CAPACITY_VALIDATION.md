## 公共修复设计

地图按世界坐标空间分块保存，维护细地图和配准地图两个分辨率层。普通地图保持
6 厘米、稠密地图保持 2 厘米的保留分辨率；稠密模式的配准仍为 15 厘米。
只有新点触及的块重新做体素合并；扫描配准只查询机器人当前位置附近的块，
避免每个关键帧都拼接、下采样或扫描整张大地图。选用公共配置决定密度，
不对某个地图改变密度或匹配门限。
体素以地图坐标中的固定网格分组，同一体素保留观测的累计质心，避免旧算法随整图边界变化
重新划分体素。旧地图文件不被重新采样；保存新地图时直接写入完整细地图快照，不再二次降采样。

旧 `max_map_points` 阈值保留为容量告警：达到后继续接收合格关键帧，不再因该阈值
冻结地图，不删除旧区域，也不自动增大体素。空间分块控制每次更新的处理范围，
不意味着机器内存无限；实际可建范围仍取决于可用内存与场景复杂度，需实机验证。

全图发布、PCD 保存从带版本的地图快照构造，避免每次定位访问都产生全图副本。
保存时仍走原有 bundle 校验、地面对齐、起点坐标变换和版本保留流程，
栅格与 PCD 必须来自一致快照。旧地图定位仍沿用原有公共加载和配准流程，
重复加载不会替换原 bundle 或改变其坐标系；本次分块增量更新用于公共建图路径。

未被合格扫描接纳的几何不能仅凭此次修复恢复。已有地图仍可正常定位和导航，
但原来预算耗尽后未采集的区域需要重新建图；新建地图自动使用公共修复。

## 本地与 ROS 验证

离线 Python 3.12 / Open3D 0.19.0 和真实 ROS2 Humble / Ubuntu Open3D 0.14.1
均通过72项单元测试。沿用已有官方ROS基础验证镜像，禁网运行并只读挂载仓库；
线程限制为 `OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1`。通过范围包括：

- 实际构造1,000,001个细地图点，跨过旧百万点阈值，旧区域和新增区域均保留；
  固定2厘米分辨率，粗配准缓存独立；负坐标、块边界、重访去重、局部查询、快照版本和并发缓存保护。
- `mapping_capacity_smoke.py`：standard / dense × capacity_alpha / capacity_beta 四组合。
  将告警阈值设为200以覆盖原停止分支；真实DDS/TF/GICP跨阈值后继续增长、旧/新增几何完整、
  静止锚点不漂、完整PointCloud2发布与原始/对齐bundle保存。分别注入地图/网格准备失败，
  验证已提交地图、起点、关键帧和位姿不被部分修改；模拟准备过慢时仍拒绝过期结果并可恢复。
- `ros_smoke.py` 标准/稠密建图、保存重载、手动/自动定位、完整三维高度与地图TF，
  `mapping_stationary_smoke.py` 静止补图、正常走转及异常跳变拒绝。
- `map_start_localization_smoke.py`、`navigation_grid_ros_smoke.py`：多地图、原始/已对齐版本、
  重复加载、真实PCD地面、机身及footprint高度；公共地面对齐和地图保存起点保持一致。
- `navigation_launch_smoke.py`、`navigation_clock_smoke.py`：mapping/localization/navigation
  两种密度参数及Nav2启动门；轻微未来TF与混合时钟偏差修复保留。
- `localization_hold_smoke.py`、`localization_patrol_smoke.py`、`navigation_pose_route_smoke.py`、
  `localization_pause_smoke.py`、`localized_control_smoke.py`：受限保持、传感器/心跳超时、
  多航点保留和显式恢复，及失效后不回放旧速度命令。

云端x86_64性能核对：一百万点的20×20米平面、1万分散更新点触及16个6米块时，
仅体素聚合更新的三次测量中位数由1.624秒降至0.214秒；优化使用有序分组和连续累计，
不改变分辨率。此值不含GICP/保存和全图发布，不代表Jetson速度，也不保证所有场景满足1秒期限。
数据准备和GICP结果的新鲜度检查仍保留，超时不会以“成功更新”掩盖。

在已有Humble SDK环境可复现核心回归：

```bash
cd /opt/go2_project
source /opt/ros/humble/setup.bash
source /ros2_ws/install/setup.bash
export OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1
python3 -m unittest discover -s tests -v
python3 tests/mapping_capacity_smoke.py
```

完整构建脚本已登记新的ROS容量回归。本次没有执行完整机器狗SDK镜像构建和完整Nav2规划控制闭环。

本次尚未在真实机器狗上验证。Jetson 长路线的内存、配准延迟、TF 新鲜度、
连续地图覆盖和实际定位/行走稳定性仍需实机确认；本地或合成 ROS 结果不能替代这些检查。

## 更新与运行

先结束旧建图或导航进程，再在机器人上执行：

```bash
cd ~/go2_nav
git pull --ff-only
bash go2_3d/run.sh mapping dense MAP_NAME
```

`MAP_NAME` 替换为本次要保存的地图名；它只是输出选择，不触发专用修补。
保存地图后仍按既有导航流程启动，将狗放回所选地图保存的原建图起点并保持原朝向，
等待合格定位，收集航点后显式启用运动。

本次不引入镜像依赖；现有镜像已具备所需 Nav2 插件时无需重建。

## 本次重定位的实际范围

系统先按所选地图保存的起点或显式初始位姿完成首次 GICP 定位。只有建立过可信定位后，
后续丢失才进入自动恢复；未完成初始定位时不会在全图盲目挑一个位置出发。
正常跟踪的重叠率、残差、静止跳变限制，以及原来的扫描/里程计新鲜度要求保持不变。

恢复以最后可信的 map→odom 和当前扫描时刻的真实里程计预测为中心，在所选地图附近搜索多个 XY/朝向初值，
以粗到细 GICP 逐一验证。地图点云只读，不切换地图，不修改保存文件，也不把被拒绝的候选当成新可信参考。
搜索限制、点数预算及较粗体素只作用于恢复后端，不降低保存的 PCD 密度。

局部搜索后端的默认恢复条件如下，均由公共 mapper 参数 `recovery_*` 控制，对所有所选地图一致生效：

| 条件 | 默认值 |
| --- | --- |
| 相对可信里程计预测的位移/旋转上限 | 2 米 / 20°；垂直偏移另限 0.35 米。 |
| 多初值搜索步长 | XY 每 0.5 米、朝向每 10°；最多对 4 个分离候选做 GICP 精配准。 |
| 可信参考最长保留时间 | 60 秒；超过后要求显式初始化，不能无限沿用陈旧参考。 |
| 几何接受条件 | 双向重叠率至少 55%，非地面结构重叠至少 50%，RMSE 不超过 0.18 米，且结构可观测。 |
| 跨扫描确认 | 至少 3 个不同时间戳的新鲜扫描；相邻确认相隔至少 0.15 秒，间隔超过 2.5 秒重新累计。 |
| 跨扫描修正一致性 | 在真实里程计运动补偿后，位移差不超过 0.18 米、旋转差不超过 3°。 |

如果多个不同候选分数接近、只有地面或几何退化，恢复维持未确认状态。
计算完成后还会再次检查扫描年龄、当前里程计与累计运动预算；
超时结果、手动初始位姿之前启动的结果和已被新跟踪状态取代的结果均不能提交。
如果正常跟踪先恢复，也要以多帧一致的新数据重新确认；不能用迟到的后台结果覆盖它。
正常跟踪的恢复证明另要求重叠率至少 55%、RMSE 不超过 0.18 米；原有较低重叠的巡检跟踪门限不变，
但这些较弱的跟踪结果不会直接授权自动续航。

恢复计算在独立工作线程执行，默认每秒至多提交一次搜索，不阻塞正常云/TF订阅。
定位恢复搜索占用计算时隙时，暂停重复执行常规 GICP，持续接收点云和里程计；
搜索结束后处理最新扫描，避免两个重型求解器同时争抢算力导致恢复结果过期。
机器人算力不足导致结果超过原有一秒新鲜度时，会明确丢弃该结果，而不会延长期限伪造恢复成功。

## 状态查看

Foxglove 已允许 `/localization/*`，可直接添加 `/localization/recovery` 文本面板。
该话题是 `std_msgs/String`，内容为 JSON；与 `/localization/valid` 和 `/operator/status` 一起查看：

| 字段/状态 | 含义 |
| --- | --- |
| `state=searching` | 尚未找到或确认可信恢复；具体原因见 `reason`。 |
| `state=confirming` | 正在累计多个不同扫描的一致证据，`confirmations` 显示当前数量。 |
| `state=recovered` | 本轮恢复已确认；`method` 区分 `tracking` 正常跟踪重验证与 `local_search` 多初值搜索。 |
| `state=failed` | 后台恢复错误；查看原因，路线不会因此自动启用。 |
| `state=manual_initialization` | 手动初始位姿已替代旧的自动恢复任务。 |
| `epoch` | 状态更新序号；操作节点要求暂停后的新恢复证明，忽略旧消息。 |
| `source_stamp` | 确认扫描的原始时间戳，恢复成功时提供。 |
| `processing_time`、`fitness`、`rmse` | 提供这些字段时用于诊断计算延迟及几何质量，不能单独代替整套恢复确认。 |

也可读取一次状态：

```bash
sudo docker exec go2-3d bash -c 'source /opt/ros/humble/setup.bash && source /ros2_ws/install/setup.bash && timeout 10 ros2 topic echo /localization/recovery --once'
```

`bash go2_3d/tools.sh motioncheck 30` 会一起采集恢复状态、路线状态和实际速度链。
观察已有路线的自动恢复时，继续观察当前目标；重新选点或手动控制会按规则替换这轮自动续航意图。

## 自动续航保留的是此前明确授权的路线

首次启动、只选点未启用、重启节点和新收集的路线都不会自动出发。
只有用户已经启用、正在执行的路线，因为定位失效而被暂停时，才保留这一轮自动续航资格：

1. 立即取消当前 Nav2 action，并通过真实参数服务禁用运动桥；保留当前未完成航点及后续航点。
2. 等待本轮新的重定位恢复结果，至少三帧确认；旧的恢复消息或一次 `valid=true` 不足以继续。
3. 定位、TF、当前目标和机器人所在格持续合格至少一秒；旧 action 的取消和运动禁用回读必须完成。
4. 清理全局、局部 Nav2 代价地图；两个服务都成功后，等待清理后生成且新接收的栅格。
5. 再次检查条件，然后重新启用运动桥，以保留的当前航点重新提交 action、重新规划。

机器人必须处于当前静态地图及两个代价地图的有效自由区域，目标必须通过静态地图和全局代价地图检查；
目标落入滚动局部窗口时也要通过局部检查，远处目标由 Nav2 沿路径检查局部障碍。
清理旧代价地图前先检查静态地图与新鲜 TF，清理并收到新栅格后再做完整检查，避免旧位姿留下的幽灵障碍永久阻塞恢复。
未知、占据或高代价格不能借重定位绕过。重新规划失败、目标不可达或普通 Nav2 action 失败不会自动无限重试。
恢复不重放暂停前的旧速度，也不会把真实 `ABORTED` 改写成到达成功。

手动停止/禁用、取消、重新选点、手动发布初始位姿、手动重试或启用都会结束旧的自动续航意图，
以本次用户操作为准。等待超过默认 60 秒、重定位失败、代价地图清理失败或其他恢复条件不满足时，
路线保留但维持暂停；查看原因后再显式启用或取消。

若一次恢复证明到达操作节点时已经超过一秒，仍拒绝该旧证明，但会去重并限频请求 mapper 用新扫描再次验证。
这避免出现 mapper 已恢复正常跟踪、操作节点却永远等不到下一份证明的状态；重新请求不延长原来的 60 秒续航授权窗口。
`/operator/status` 还会显示当前等待阶段、证明序号、剩余时间和具体阻塞条件，包括运动禁用/取消尚未完成、
TF 或栅格过期、机器人/目标单元不可用、代价地图未刷新等。状态仅在等待原因变化或每五秒更新，避免高频输出增加负载。

操作节点启动参数如下。它们控制路线恢复，不修改正常定位的接受门限或运动速度。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `auto_resume_localization` | `true` | 允许恢复此前已经启用并执行、仅因定位丢失而暂停的路线。 |
| `auto_resume_stable_seconds` | `1.0` | 恢复后条件必须连续稳定的时间，不能小于一秒。 |
| `auto_resume_timeout` | `60.0` | 保留本轮自动续航资格的最长等待时间。 |

## 更新与验证

更新代码后要重启 mapper 和操作节点，已经运行的旧进程不会自动加载新逻辑。
重启后的路线队列为空，需重新选点并显式启用一次；这与运行中定位丢失后的自动续航不同。
已有镜像具备原建图/定位依赖时，本次 Python 修改无需重新制作地图或仅为此重建镜像。

离线算法回归使用仓库 Python 依赖：

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 python3 -m unittest discover -s tests -v
```

在已激活 ROS2 Humble、Nav2/Unitree 消息依赖的环境中，分别验证真实 GICP 恢复和操作节点的 ROS action/参数服务流程：

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 python3 tests/relocalization_smoke.py
python3 tests/automatic_resume_smoke.py
```

这两项仍使用合成传感器和受控端点；操作节点回归里的恢复事件由测试端发送，不能单独证明真实扫描定位正确。
现场应同时记录 `/localization/recovery`、`/localization/state`、`/operator/status`、实际 map→odom、
当前航点及机器狗实际运动。分别验收正常重新捕获、无法确认的重复场景保持停止，以及手动停止后不再自动恢复旧路线。

本次云端通过的检查包括：

- 完整 104 项离线测试，分别使用 Open3D 0.19 和 ROS Humble 的 Open3D 0.14.1。
- 真实 ROS/GICP 的约 1.8 米里程计偏差丢失与重新捕获；两个不同地图名的原始图和地面对齐图，
  并检查机身/footprint、重复加载、地图文件不变、扫描超时以及手动初始位姿废弃旧后台结果。
- 正常跟踪的恢复请求需三帧新鲜质量证据；原始图使用单包，地面对齐图使用实际导航的 0.5 秒多包累积。
- 真实 ROS action、参数服务、双代价地图清理的自动续航流程，以及停止/取消/新目标/手动初始位姿、
  二次失效、旧证明、旧栅格、真实障碍、普通导航失败和服务缺失的拒绝路径。

云机四核配额下曾出现里程计超过原有 0.3 秒时效、导致连续有效性测试失败；没有放宽时效或断言。
去掉不必要的周期恢复状态广播后，默认两线程下的巡检与原始/对齐地图转弯回归通过。
机器狗电脑的搜索耗时与现场恢复成功率仍需实测；这些检查未运行真实 Nav2 规划控制闭环或实机运动。

## 需要分别判断的结果

定位恢复首先要回答“当前扫描在所选地图中的哪个位置可信”，路线恢复再回答“此前授权的剩余路线现在是否还能执行”。
两者均应使用当前数据和当前地图，而不能依赖曾经出现过一次的 `valid=true` 或已经缓存的旧速度。
所有地图名、新图和历史版本共用公共处理路径，不写入农场专属坐标或某张图的例外。

重复树行、只有平面地面、遮挡、严重点云畸变，或机器人被搬离最近可信位置较远时，都可能无法自动恢复。
有界局部搜索不等于任意位置全图重定位；停止并持续报告无法恢复的原因是合法结果。
截图和上游项目演示不能证明当前农场的误匹配率与实际运动安全性，需要保留本次原始传感器记录并做现场验收。

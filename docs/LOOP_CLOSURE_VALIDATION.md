# 通用回环建图与农场验证

本次修改针对公共建图流程。所有地图名、新保存版本，以及 standard/dense 建图使用同一套回环逻辑；
不使用某张地图的文件名、农场起点坐标或固定地面高度识别回环。定位和导航继续读取公共保存流程输出的地图，
不修改原有运动参数、定位接受门限或建图保存分辨率。

## 回环修正的范围

前端仍用时间戳对齐的里程计预测和三维 GICP 累积观测。后端保留关键帧的局部几何，
用按半径和方向组织的高度/占据描述检索相似历史地点，不按当前世界坐标距离限制候选，
因此累计漂移后仍可搜索起点。候选先估计相对朝向，再经过粗到细的 GICP 几何验证。
除双向整体重叠率和残差外，还单独检查非地面结构重叠与几何可观测性，避免大片地面造成虚假的高匹配分数。
后端排除相邻关键帧和过短行程的重复观测，并用两个有空间间隔的再次观测及其修正一致性确认回环。
重复树行中多个地点同样相似、只有平坦地面或可用几何不足时，应拒绝回环，而不是强行把终点拉回起点。

验证通过后优化完整位姿图，固定首帧坐标，将误差沿历史轨迹分配。
所有参与建图的观测按修正后的位姿重新累积，保留原来的细点云密度；
自由空间按修正后的传感器位置与观测射线重新计算，不能只挪动 PCD 或旧栅格。
完整修正结果与实时 map→odom 一起提交，保存时再通过原有公共流程生成地面模型、导航栅格和站立起点。

原始保存版本与历史地图不会被覆盖。只有融合 PCD、没有当次逐帧观测和轨迹的旧地图，
不能自动反推并消除已经融合进去的非刚性漂移；需要重新采集建图。
这与旧地图能否正常加载、地面对齐和定位是不同问题。

## 农场现场操作

先停止旧建图/导航终端，把机器狗放在有明显几何特征的起点。
尽量选择能同时看到路口、建筑边角、立柱或不规则树丛的位置，避免只以一段重复树行作为起点。
在机器狗扩展电脑执行：

```bash
cd ~/go2_nav
git pull --ff-only
bash go2_3d/run.sh mapping dense
```

本次回环实现复用镜像已有的 Open3D、NumPy 和 PyYAML，代码由仓库挂载加载；
已有可正常建图的镜像无需仅为这些 Python 代码重建。首次安装和镜像缺少原有依赖时仍按 README 执行构建。

用遥控器慢速完成约 200 米环线，转弯时保留对周围场景的扫描。
回到起点后沿起步方向再经过几米，使后端能用两个有空间间隔的观测确认同一历史区域；
随后保持站立，查看 Foxglove 的 `/mapping/loop_closure` 文本话题，等待回环修正提交完成。
不要仅凭终点与起点距离很近或视觉上两段树行重合就判定成功。

该话题是 `std_msgs/String`，内容为 JSON。现场重点看以下字段：

| 字段 | 含义 |
| --- | --- |
| `applied_loops` | 已完成整图重建并提交的优化次数。大于零才说明本次建图已实际应用回环修正。 |
| `state` | `checking` 为检测中，`rebuilding` 为重建中，`applied` 为刚提交，`idle` 为本轮检查结束。`idle` 本身不代表发生过回环。 |
| `checked_observations` / `observations` | 已检查与已接收的建图观测数。两者相等且无错误时，后台才追上当前观测。 |
| `backend.state` / `backend.reason` | 几何检测的结果与原因。`confirming` 表示仍需再次经过；`rejected` 表示候选未通过验证。 |
| `last_loop` | 最近一次成功优化的摘要与整图重建耗时。 |
| `error` | 后台计算错误；非空时先处理原因，不把当前地图当作已完成回环的结果。 |
| `retained_scan_bytes` | 为重建保留的原始观测所占内存字节数，不含全部地图及配准临时内存。 |

也可在第二个 SSH 终端读取一次状态：

```bash
sudo docker exec go2-3d bash -c 'source /opt/ros/humble/setup.bash && source /ros2_ws/install/setup.bash && timeout 10 ros2 topic echo /mapping/loop_closure --once'
```

保存前确认 `applied_loops>=1`、`checked_observations=observations`、
`state` 为 `idle` 或 `applied`，且 `error` 为空。若没有通过几何验证，普通增量地图仍可能保存成功，
因此 `success=True` 与“发生过回环”也要分别确认。

确认闭环提交后，在第二个 SSH 终端保存：

```bash
cd ~/go2_nav
bash go2_3d/tools.sh save
```

只有 `success=True` 才表示保存成功。保存失败时保留建图进程，读取返回原因；
若后端仍在检测或重建，先等待完成，再保存。
保存的 `metadata.yaml` 中 `loop_closure` 记录该地图快照对应的回环状态，原始版与地面对齐版都保留这份记录。
随后回到建图终端按 Ctrl+C。把机器狗放回该图记录的起点和朝向，再启动：

```bash
bash go2_3d/run.sh navigation dense
```

等待 GICP 定位有效和 Nav2 启动成功，再在新图中重新选择目标并显式启用运动。

## 现场验收需要记录的结果

- 回环状态中的已提交次数及候选/拒绝原因，区分识别到候选和整图修正完成。
- 起点附近同一立柱、树干或墙角在回环前后的重复轮廓间距，以及整圈中间位置是否出现明显扭曲。
- 保存成功后的地图版本及元数据；重新加载后检查三维地图、导航栅格和机身高度仍在同一坐标系。
- 实际行走一圈的耗时、机器狗电脑上的计算延迟，以及地图重建期间前端是否持续接受新观测。

约 200 米是现场路线长度，不是算法能对所有场景保证的闭环距离。
农场重复树行、风吹植被、遮挡、观测朝向变化、里程计异常和点云畸变都可能导致拒绝回环或误匹配风险。
截图不能替代原始扫描与轨迹验证；云端合成测试和 ROS 接口测试也不能替代本次实地验收。

## 本次云端验证结果

- Python 3.12 / Open3D 0.19：完整 88 项单元测试通过。覆盖 200 米合成环线的米级累计漂移、
  180° 返回、第二圈不重复施加前圈修正、确认过期、重复地点歧义拒绝、平地/稀疏点云拒绝，
  以及后台重建期间新增扫描不丢失、失败不提交、自由空间重新投射。
- ROS2 Humble / Python 3.10 / Open3D 0.14.1：85 项当时完整测试及最终 9 项回环测试通过。
  standard/dense 的真实 ROS 建图、定位、TF、保存回归，以及两个地图名称的两种密度容量回归通过。
- `tests/mapping_loop_smoke.py` 使用真实回环检测和优化后端，将合成 200 米轨迹的 42 次观测
  重建并保存为地面对齐地图，检查实际 ROS 点云、map→odom、起点和时效预算。
  该测试直接输入观测记录，前端实时 GICP 由原有 ROS smoke 单独覆盖；没有运行完整 Nav2 控制或机器狗。

这些是固定合成几何下的行为回归，不是现场厘米级精度声明。闭环约束能够收拢首尾并调整历史轨迹，
但没有外部真值或更多独立约束，不能保证所有中间点的真实位置误差都降低。
机器狗上完成 `git pull --ff-only` 后，重新启动建图进程才会加载新代码；已有建图进程不会自动更新回环后端。

# DDS 传感器时间转换修复

现场反复出现 `odom_age=-0.11..-0.17s`，表示转换后的里程计时间位于主机未来，
并非旧数据。它超过既有 100ms 未来时间容差后使定位无效，路线暂停；短暂恢复又失效，
无法满足自动恢复证明。地图和路径能显示，不代表该时序检查正常。

旧 SensorClock 将第一帧的“主机收包时间减传感器时间”永久作为公共偏移。
已复现首帧额外排队 170ms、后续正常接收时，里程计超前 170ms，早 60ms 的云超前 110ms。
历史 11 月 5 日也有这段实现，因此仅恢复控制器和 GICP 不能修复这个接口缺陷。
现场原始时钟证据尚不足以排除额外漂移；本补丁针对已复现的首帧偏差，并增加时序证据。

## 修复边界

- 启动先观察至少 0.5 秒、至少 5 个递增的原始里程计样本，选取最小收包偏移；校准完成前不转发传感器数据。
- 校准后冻结一个公共偏移，供 odom、TF 和云共用，保留原始采样间隔及几何；不逐包改成当前时间。
- 延迟增大、断流、重复/乱序、过旧和超前样本不会重新校准或刷新运动桥接收时间。
- 超前坏帧被丢弃后，正常帧可以恢复；坏帧不推进已接受的时间边界。
- 用单调时钟前后夹取 ROS 时钟；采样跨度超过 20ms 时丢弃不精确的观测，不将调度抢占误判为时钟跳变。
- 检测到真实主机时钟跳变时停止转发，保留原有停止保护；不能在活动 TF 历史中突然重设偏移。
- `/control/status` 和故障日志记录原始时间、转换时间、主机接收时间、校准状态及拒绝原因。

11 月 5 日恢复后的 GICP、定位阈值、官方控制器、点位队列、三次重试均未修改。
本补丁是挂载源码中的 Python 修改，现有导航镜像无需重建。必须结束旧导航进程再启动，
让新的桥从启动阶段重新校准；仅 `git pull` 不会替换正在运行的节点。

## 验证

纯时钟回归覆盖首帧 170ms 排队、两路相对时间、断流/旧帧/乱序、未来坏帧后恢复、
实际主机时钟步进以及 200ms 调度抢占不产生永久时钟故障。
真实 ROS/Unitree 消息回归验证转发、TF、几何保持和停止边界，不连接机器狗。
软件测试不是实机百米巡检验证，后续现场仍以自动保存的故障证据为准。
